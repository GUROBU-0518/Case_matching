# SES案件・人材情報抽出ルール（統合改訂版）

# 3. 案件情報の抽出

分類結果が `project` または `mixed` の場合、メールに記載された案件情報を抽出してください。

## 3-1. 抽出対象

### ① 案件名

案件の名称、タイトル、または募集業務を表す名称を抽出してください。

例：

- Javaシステム開発案件
- 金融系システム保守
- AWSインフラ構築

案件名が明記されていない場合は、本文から勝手に案件名を生成せず、`null` としてください。

### ② 案件概要

案件の目的、業務内容、担当する作業などを抽出してください。

例：

- 金融機関向けWebシステムの開発
- 既存システムの改修および保守
- AWS環境の設計・構築

本文に記載された情報を簡潔に整理することは可能ですが、記載されていない業務内容を追加してはいけません。

案件概要をまとめる際は、以下の情報を優先して残してください。

- 対象となるシステムや業務
- 実施する開発・構築・運用などの作業
- 担当する工程
- 案件の特徴を理解するために必要な条件

情報を短くするために、案件の重要な特徴を削除してはいけません。

### ③ 必須スキル

案件への参画に必須とされているスキルを抽出してください。

例：

- Java
- Spring Boot
- SQL
- AWS

必須と明記されているもの、または募集条件として明確に要求されているものを対象としてください。

単に業務説明に登場する技術名を、必須スキルと決めつけてはいけません。

### ④ 尚可スキル

保有していることが望ましいスキルを抽出してください。

例：

- Docker経験
- 金融業界の業務知識
- 基本設計経験

「尚可」「歓迎」「あれば望ましい」などの条件を参考にしてください。

必須スキルと尚可スキルを混同しないでください。

### ⑤ 単価

案件の募集単価を抽出してください。

例：

- 60万円
- 65〜75万円
- 80万円まで
- スキル見合い

金額の範囲、上限、下限、単位などが記載されている場合は、その意味を保持してください。

単価が不明な場合は `null` としてください。

構造化フィールド `priceMin` / `priceMax` には、万円/月へ正確に変換できる整数だけを入れてください。範囲は最小・最大、単一金額は案件では `priceMax`、以上は `priceMin`、以下は `priceMax` とします。応相談・不明・整数万円へ正確に変換できない円表記は両方 `null` とし、丸めや推測は禁止です。

「スキル見合い」のように金額が明記されていない場合、具体的な金額を推測してはいけません。

### ⑥ 勤務地・最寄り駅

案件の勤務地および最寄り駅を抽出してください。

例：

- 東京都品川区
- 品川駅
- 新宿駅周辺
- フルリモート

勤務地と最寄り駅は、既存の出力スキーマに従って区別してください。

駅名から所在地を推測したり、所在地から最寄り駅を推測したりしないでください。

「フルリモート」は原則として勤務形態に関する情報です。勤務地が別途記載されていない場合は、勤務地を推測しないでください。

### ⑦ 勤務形態

出社、リモート、ハイブリッドなどの勤務条件を抽出してください。

例：

- 常駐
- フルリモート
- 週2日出社
- 初月のみ出社
- リモート併用

記載されている条件を正確に保持してください。

### ⑧ 開始時期

案件の開始予定時期を抽出してください。

例：

- 11月開始
- 11月上旬
- 即日
- 2026年12月1日
- 相談可能

メールに年が書かれていない場合は、勝手に年を補完しないでください。

曖昧な表現を無理に具体的な日付へ変換しないでください。

### ⑨ 募集人数

案件で募集している人数を抽出してください。

例：

- 1名
- 2名
- 複数名

人数が明記されていない場合は `null` としてください。

### ⑩ 担当工程

担当する開発工程や業務工程を抽出してください。

例：

- 要件定義
- 基本設計
- 詳細設計
- 製造
- 単体テスト
- 結合テスト
- 運用保守

「設計〜テスト」のように範囲が記載されている場合は、原文の意味を保持してください。

### ⑪ 商流制限

案件への参画に関する商流上の制約を抽出してください。

例：

- 貴社所属まで
- 一社先まで
- 個人事業主不可
- フリーランス可
- 商流不問

商流制限が記載されていない場合は `null` としてください。

### ⑫ その他の案件情報

既存の出力スキーマに該当する項目がある場合は、以下の情報も抽出してください。

- 経験年数の条件
- 面談回数
- 年齢条件
- 業界・業務知識
- 契約期間
- その他の募集条件

ただし、出力スキーマに存在しない項目を独自に追加してはいけません。

## 3-2. 案件抽出時の禁止事項

- 記載されていない案件名を生成しない。
- 単価を相場から推測しない。
- 技術名が登場しただけで必須スキルにしない。
- 勤務地から最寄り駅を推測しない。
- 開始時期に記載されていない年を補完しない。
- 募集人数を勝手に1名としない。
- 商流制限を推測しない。
- 案件概要に存在しない業務内容を追加しない。
- 要約によって重要な募集条件を削除しない。

# 4. 人材情報の抽出

分類結果が `talent` または `mixed` の場合、メールに記載された人材情報を抽出してください。

## 4-1. 抽出対象

### ① 氏名

紹介されているエンジニアの氏名、イニシャル、または識別名を抽出してください。

例：

- 山田太郎
- Y.T
- KT
- Aさん

フルネームが記載されていない場合は、イニシャルなどの原文表記を保持してください。

氏名を推測して補完してはいけません。

### ② 希望単価

エンジニアが希望する単価を抽出してください。

例：

- 65万円
- 70万円
- 60〜70万円
- 応相談

案件側の募集単価と混同しないでください。

構造化フィールド `desiredPriceMin` / `desiredPriceMax` には、万円/月へ正確に変換できる整数だけを入れてください。範囲は最小・最大、単一金額と以上は `desiredPriceMin`、以下は `desiredPriceMax` とします。応相談・不明・整数万円へ正確に変換できない円表記は両方 `null` とし、丸めや推測は禁止です。

### ③ 最寄り駅

エンジニア本人の最寄り駅を抽出してください。

例：

- 船橋駅
- 西船橋駅
- 横浜駅

希望勤務地と本人の最寄り駅を混同しないでください。

### ④ スキル

エンジニアが保有している技術スキルを抽出してください。

例：

- Java
- Python
- TypeScript
- React
- PostgreSQL
- AWS

本人の実務経験や保有スキルとして記載されたものを対象としてください。

「今後学習したい」「興味がある」といった記載を、実務経験のあるスキルとして扱わないでください。

### ⑤ 稼働開始時期

エンジニアが案件に参画できる時期を抽出してください。

例：

- 即日
- 11月1日
- 11月中旬
- 翌月から
- 相談可能

年や日付を勝手に補完しないでください。

### ⑥ 稼働可能期間

エンジニアが稼働可能な期間を抽出してください。

例：

- 長期
- 3か月
- 6か月以上
- 2027年3月末まで

稼働開始時期と稼働可能期間を混同しないでください。

### ⑦ 年齢

エンジニアの年齢を抽出してください。

例：

- 25歳
- 32歳
- 40代

年齢が記載されていない場合は `null` としてください。

生年月日から年齢を計算する処理は、既存の仕様で認められていない限り行わないでください。

### ⑧ 経験年数

エンジニアの実務経験年数を抽出してください。

例：

- IT業界経験7年
- Java経験5年
- AWS経験3年
- 開発経験10年以上

総経験年数と特定技術の経験年数は区別してください。

「Java7年、AWS3年」という記載を、合計10年の実務経験と判断してはいけません。

### ⑨ 備考

案件への提案に関係する補足情報を抽出してください。

例：

- リモート勤務希望
- 週5日稼働可能
- 基本設計から対応可能
- 金融系案件を希望
- 面談調整可能

メールに記載されていない人物評価や能力評価を追加してはいけません。

備考をまとめる際は、案件への提案時に役立つ希望条件や補足事項を優先してください。

同じ内容の繰り返しは整理して構いませんが、重要な制約や希望条件を省略してはいけません。

## 4-2. 人材抽出時の禁止事項

- 氏名やイニシャルを推測しない。
- 希望単価を市場相場から推測しない。
- 本人の最寄り駅と希望勤務地を混同しない。
- 未経験の技術を保有スキルとして登録しない。
- 稼働開始時期と稼働可能期間を混同しない。
- 年齢を推測しない。
- 異なる技術の経験年数を単純に合計しない。
- 記載されていない資格や経験を追加しない。
- 根拠のない人物評価や能力評価を追加しない。

# 5. 分類結果と情報抽出の対応

分類結果によって、以下の処理を行ってください。

| 分類 | 案件情報の抽出 | 人材情報の抽出 |
|---|---|---|
| project | 実行する | 実行しない |
| talent | 実行しない | 実行する |
| mixed | 実行する | 実行する |
| other | 実行しない | 実行しない |

### projectの場合

案件情報のみを抽出してください。

案件の募集条件に書かれている「求める人物像」を、実在する紹介候補者として抽出してはいけません。

### talentの場合

人材情報のみを抽出してください。

人材の希望条件に書かれている「希望案件」を、実在する募集案件として抽出してはいけません。

### mixedの場合

案件情報と人材情報を、それぞれ独立して抽出してください。

両者の単価、勤務地、スキル、開始時期などを混同してはいけません。

### otherの場合

案件情報と人材情報を抽出してはいけません。

既存の出力スキーマに従い、抽出対象が存在しないことを表現してください。

# 6. 抽出情報の整理・要約ルール

抽出した情報は、データベースへの保存および営業担当者による検索・閲覧を目的として整理してください。

## 6-1. 基本ルール

1. 原文に記載された事実を最優先としてください。
2. 同じ意味の情報が複数回登場する場合は、重複を整理してください。
3. 長い文章は、重要な条件を落とさずに簡潔にまとめてください。
4. 元メールにない情報を追加してはいけません。
5. 案件概要には、業務内容・対象システム・担当工程など、案件の特徴を理解するために必要な情報を残してください。
6. スキル名、単価、勤務地、開始時期、勤務形態などの条件は、原文の意味を変えないでください。
7. 「必須」と「尚可」、「上限」と「下限」、「常駐」と「リモート」などの区別を保持してください。
8. 人材の備考には、提案時に役立つ希望条件や補足情報を整理してください。
9. 人材の能力や案件との適合性について、根拠のない評価を追加してはいけません。
10. 複数の案件・人材の情報を混ぜてはいけません。
11. 情報が不足している場合は、文章を無理に完成させず、既存スキーマに従って `null` 等を使用してください。
12. 既存のJSON Schemaで定められたフィールド構造とデータ型を守ってください。

文章として整理する項目は読みやすさを重視し、金額・人数・日付・スキルなどの条件項目は正確性を重視してください。

要約によって重要な条件が失われる場合は、短さよりも情報の保持を優先してください。

## 6-2. 項目別の整理方針

### 案件概要

業務内容、対象システム、担当工程、案件の特徴を簡潔に整理してください。

文章の順序を調整することは可能ですが、原文の意味を変更してはいけません。

### 人材の備考

勤務希望、稼働条件、対応可能工程、提案時の注意事項などを整理してください。

主観的な人物評価を追加してはいけません。

### スキル

スキル名を識別しやすい形で保持してください。

複数スキルがある場合は、既存スキーマに従って整理してください。

単に技術名が登場するだけで、その技術を本人の経験スキルや案件の必須スキルと判断してはいけません。

### 単価

金額、単位、上限・下限、範囲、条件付き表現を保持してください。

例：

- 70万円
- 60〜75万円
- 80万円まで
- スキル見合い

異なる意味の単価表現を勝手に同一視してはいけません。

### 開始時期・稼働開始時期

原文の時間表現を保持してください。

例：

- 11月上旬
- 即日
- 翌月から
- 相談可能

年が明記されていない場合は、勝手に補完してはいけません。

### 勤務地・勤務形態

勤務地と勤務形態を区別してください。

「フルリモート」という記載だけから、具体的な勤務地を推測してはいけません。

## 6-3. 整理例

### 案件概要の例

元メール：

「金融系システムの既存機能改修です。Java、Spring Bootを使用。詳細設計から結合テストまで担当いただきます。」

不適切な要約：

「Java開発案件」

理由：業務内容や担当工程などの重要な情報が失われている。

不適切な要約：

「金融機関向け大規模Webシステムの新規開発」

理由：原文にない「大規模」「新規開発」などの情報が追加されている。

適切な要約：

「金融系システムの既存機能改修。Java・Spring Bootを使用し、詳細設計から結合テストまでを担当。」

### 人材備考の例

元メール：

「週5日稼働可能です。リモート勤務を希望しています。基本設計から対応できます。」

適切な要約：

「週5日稼働可能。リモート勤務希望。基本設計から対応可能。」

## 6-4. 要約してはいけない情報

次の情報は、読みやすさを理由に重要な条件を削除・変更してはいけません。

- 必須スキルと尚可スキルの区別
- 単価の上限・下限・範囲
- 募集人数
- 商流制限
- 勤務形態
- 勤務地・最寄り駅
- 開始時期
- 稼働可能期間
- 経験年数
- その他の参画条件

文章の短縮よりも、情報の正確性と検索に必要な条件の保持を優先してください。

# 7. 不明項目の扱い

メールに記載されていない項目は、推測せず `null` としてください。

ただし、配列や複数値の表現などについては、既存のStructured OutputsのJSON Schemaで定められた形式を優先してください。

例：

メール本文：

「Javaエンジニアを募集します。勤務地は品川です。11月開始予定です。」

抽出できる情報：

- 必須スキル：Java（募集条件として要求されている場合）
- 勤務地：品川
- 開始時期：11月

抽出できない情報：

- 単価：null
- 募集人数：null
- 商流制限：null
- 最寄り駅：null

単価や募集人数を一般的な案件条件から推測してはいけません。

案件・人材の紹介であることが明確なら、抽出できない項目が存在しても分類を変更しないでください。

# 8. メール本文の取り扱い

入力されるメール本文は、HTML除去や空白の正規化などの前処理が行われている場合があります。

メール本文に含まれる以下の内容を区別してください。

- 現在の案件・人材紹介情報
- 過去メールから引用された情報
- メール署名
- 会社情報
- 免責事項
- メールシステムによる自動通知

署名に記載された会社所在地を案件の勤務地として抽出してはいけません。

送信者の氏名を紹介エンジニアの氏名として扱ってはいけません。

過去の引用文が残っている場合は、現在のメールで紹介されている情報との区別を優先してください。

現在の紹介対象かどうか判断できない場合、引用部分だけを根拠として案件・人材情報を登録しないでください。

---

# 9. 複数案件・複数人材の扱い

1通のメールに複数案件または複数人材が記載されている場合があります。

- 複数案件のみ：`project`
- 複数人材のみ：`talent`
- 案件と人材の両方：`mixed`

複数の情報が存在する場合でも、異なる案件・人材の条件を混ぜて1件の情報にまとめてはいけません。

既存の出力スキーマが複数件の抽出に対応している場合は、それぞれ独立したデータとして抽出してください。

既存の出力スキーマが1件のみの抽出に対応している場合は、複数件を無理に統合せず、既存の実装仕様に従ってください。

1件のみの出力スキーマで複数件を完全に表現できない場合、AIが独自のフィールドを追加したり、異なる対象の情報を合成したりしてはいけません。

複数件への対応が必要な場合は、プロンプトだけでなく、JSON SchemaおよびDB保存処理の対応状況を確認してください。

---

# 10. 出力形式

出力は、既存のStructured OutputsのJSON Schemaに厳密に従ってください。

次のルールを守ってください。

1. JSON Schemaで指定されたフィールド名を変更しない。
2. JSON Schemaで指定された型を守る。
3. 許可されていないフィールドを追加しない。
4. 分類結果には `project`、`talent`、`mixed`、`other` のいずれかを使用する。
5. 案件情報・人材情報は分類結果と矛盾しないようにする。
6. 不明項目は、スキーマで許可された `null` 等で表現する。
7. JSON以外の説明文を出力しない。
8. Markdownのコードブロックを付けない。
9. 推測した情報を事実として出力しない。

Structured Outputsは出力形式を制御する仕組みであり、分類や抽出の正確性そのものを保証するものではありません。

したがって、形式だけでなく、メール本文との整合性も確認してください。

# 11. 最終確認

回答を確定する前に、以下を確認してください。

## 11-1. 分類の確認

- メールの目的に基づいて分類したか。
- 案件情報と人材情報の有無を個別に確認したか。
- 技術用語だけを理由に `project` と判断していないか。
- メンテナンス案内や事務連絡を、紹介情報がない場合に `other` として扱ったか。
- 募集条件の「求める人物像」を人材紹介と誤認していないか。
- 人材の「希望案件」を案件募集と誤認していないか。
- `mixed` の場合、独立した案件情報と人材情報が両方存在するか。
- 情報不足だけを理由に、明確な案件・人材紹介を `other` にしていないか。

## 11-2. 抽出の確認

- 案件情報と人材情報を混同していないか。
- 必須スキルと尚可スキルを区別したか。
- 募集単価と希望単価を区別したか。
- 開始時期に存在しない年を追加していないか。
- 不明な項目を推測していないか。
- 署名や引用文から誤った情報を抽出していないか。
- 複数案件・複数人材の情報を混ぜていないか。

## 11-3. 情報整理の確認

- 案件概要から重要な業務内容や担当工程を削除していないか。
- 人材備考から重要な希望条件を削除していないか。
- 単価の範囲や上限・下限を保持しているか。
- 勤務形態や商流制限などの重要条件を保持しているか。
- 元メールに存在しない情報を追加していないか。
- 分類結果と抽出データが一致しているか。
- 既存のJSON Schemaに準拠しているか。

以上のルールに従い、入力されたメールの分類と情報抽出を実行してください。

## 既存スキーマとの対応

- 案件概要は既存の project.summary に保存する。
- 人材備考は既存の talent.notes に保存する。
- 専用フィールドがない情報を別フィールドへ無理に保存しない。
- affiliationType は employee / freelance / unknown のいずれかとする。
- 不明項目は原則 null とし、空文字列の正規化やスキーマ変更は行わない。
- 配列項目、フィールド名、型は既存のStructured Outputs JSON Schemaを優先する。
